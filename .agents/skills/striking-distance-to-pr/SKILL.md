# OpenSEO Striking Distance to PR

## Goal

Close the loop that every SEO tool stops short of: diagnosis with no treatment. Take
one query already ranking 5-20 on the connected Search Console property, find the
page that ranks for it, write a small, human-reviewable on-page fix in the user's own
repo, verify it builds, and open a PR with the evidence for why the change should
help. One query, one page, one PR per run. This skill never edits a live site
directly and never opens a PR from anywhere but the user's own machine and their own
`gh` session.

## Why this is scoped so narrowly

- AI crawlers (GPTBot, ClaudeBot, PerplexityBot, and friends) execute zero
  JavaScript. Only a change that lands in the initial server-rendered HTML is ever
  seen by them. A merged PR does that; a client-side/edge/JS-injected change does
  not, no matter how it is described.
- A human reviews every change before it ships, because it is an ordinary PR against
  the user's own repo.
- Ahrefs' controlled study found no citation lift from FAQ/JSON-LD schema (AIO
  -4.6%), and FAQ rich results were retired in Google Search in May 2026. Schema is
  not a fix worth spending review attention on, so it is not in scope here.

## Required inputs

- `projectId` with Search Console connected (the diagnosis is entirely GSC data).
- A local git checkout of the site's repo, with `gh` authenticated for it.
- Optionally, a specific query the user already has in mind. Otherwise this skill
  picks the highest-impressions candidate automatically.

## OpenSEO MCP tools

- `whoami`, `list_projects`: preflight only, to confirm MCP and project access.
- `get_striking_distance`: the diagnosis. Free, first-party GSC, no credits. Returns
  `{query, page, clicks, impressions, position}` rows already collapsed to each
  query's single best-ranking page and filtered to the 5-20 position band, sorted by
  impressions.
- `get_serp_analysis`: the context. Metered, costs real credits per call
  (comparable to `get_serp_results`, roughly 30-60 credits). Call it exactly once,
  for the chosen query only, never for the whole candidate list.
- `get_search_console_performance`: optional, to cross-check which of the site's
  other pages already earn clicks for related queries, as candidates for internal
  links.

## Workflow

### 1. Preflight

Confirm every one of these before touching anything, and stop with a plain
explanation the moment one fails. Do not degrade to a CMS or JS-based workaround,
even if a check fails, explain why and stop:

1. OpenSEO MCP is reachable: `whoami`, then `list_projects` to resolve `projectId`
   if it was not given.
2. Search Console is connected for the project. `get_striking_distance` returning
   `ok: false, reason: "not_connected"` means it is not; tell the user to connect it
   from the project's settings page (the tool response includes the URL) and stop.
3. The current directory is inside a git repository (`git rev-parse
--is-inside-work-tree`) and the working tree is clean (`git status --porcelain` is
   empty). A dirty tree means uncommitted work could get mixed into the fix commit,
   so ask the user to stash or commit first.
4. `gh auth status` succeeds and the repo has a remote `gh` recognizes.
5. Detect the site's framework by inspecting the repo (package.json, config files,
   directory layout): Next.js, Astro, Remix, plain HTML/templates, or something
   else. Note it for step 4 (locating the source file); do not guess a framework
   you have not actually seen evidence for.

If the site is not repo-backed (no local checkout, or the page is generated by a
CMS/host this skill can't find source for), say so plainly and stop. This skill has
no CMS write path and does not claim to work everywhere.

### 2. Diagnose

Call `get_striking_distance` with the project's default date window (last 28 days
unless the user asks for a different one). Present the top 5-10 candidates by
impressions: query, page, clicks, impressions, position. Ask the user to pick one,
or offer to auto-pick the highest-impressions row if they have no preference.

Work one query/page pair per run. If the user wants more than one page fixed, run
this skill again for the next candidate after the first PR is opened.

### 3. Build context

Before writing anything:

1. Tell the user `get_serp_analysis` will spend real credits for this one query,
   then call it once for the chosen query. Read the top 3-5 results: what intent do
   they answer, what do their titles promise, how much authority (referring
   domains, backlinks) do they carry versus the user's own domain.
2. Fetch the live page's current HTML (the page from step 2) to see its current
   title, meta description, headings, and body copy exactly as shipped.
3. Locate the page's source file in the repo. This is heuristic and depends on the
   framework detected in preflight:
   - Next.js-style: a metadata export (`generateMetadata`, `metadata` object) plus
     the page component file.
   - Astro/Remix/static-site-generator: frontmatter block or a page/content file
     matching the URL's route or slug.
   - Plain HTML/templates: the literal `<title>`/`<meta name="description">` tags
     and heading markup in the matching template or static file.
4. **Show the user the file you located and ask them to confirm it before editing.**
   Do not silently guess and edit the wrong file: cross-repo routing (rewrites,
   redirects, monorepos, multiple apps) makes this genuinely ambiguous sometimes.
5. Optionally call `get_search_console_performance` with `dimensions: ["page"]` to
   find 1-3 of the site's own already-ranking pages that are topically related, as
   internal-link candidates.

### 4. Write the fix

The fix is restricted to this whitelist. Nothing outside it, even if it seems like
an easy win:

- **Title and meta description rewrite**, aligned to the chosen query's actual
  search intent (informational, commercial, navigational, transactional) as read
  from the SERP context in step 3.
- **One intent-answering H2** placed near the top of the page's existing content,
  with a direct-answer paragraph immediately under it that actually answers the
  query, not just repeats it.
- **1-3 server-rendered internal links** from the page to (or from) other relevant
  existing pages found in step 3, written as literal `<a>`/markdown link markup in
  the page or template source, not injected by client-side script.

Explicitly **not** in the whitelist, regardless of how the user or the moment
requests it:

- JSON-LD or FAQ schema blocks of any kind.
- Any client-side, JS-injected, or edge-rendered change (a script that adds links or
  content after the page has already served its initial HTML does not count; AI
  crawlers will never see it).
- Bulk or multi-page edits. One page, one PR.
- Anything not listed above (new sections, redesigns, unrelated copy edits, removing
  existing content). If the user asks for more, say it is out of scope for this
  skill and suggest they do it separately.

Make the smallest edit that satisfies the whitelist. Preserve the page's existing
voice and structure; do not rewrite paragraphs that already work.

### 5. Verify

Before proposing anything to the user or opening a PR:

1. Run the project's build (`npm run build` / `pnpm build` / the framework's
   equivalent, detected from `package.json`).
2. If the project has a fast, targeted test command for the changed area (not a full
   E2E suite), run it. Skip anything slow or flaky-by-nature; a broken build is the
   bar, not perfect coverage.
3. If the build fails, fix the fix or stop and explain the failure. Never open a PR
   with a known-broken build.

### 6. Open the PR

Create a branch, commit only the whitelisted change, push, and open the PR with
`gh pr create`. The PR body must include an evidence block with plain numbers, no
causal claims, since this is a prediction, not a result yet:

```markdown
## Striking-distance fix

**Query:** "<query>"
**Page:** <page URL>
**Current position:** <position> (avg, GSC last 28 days)
**Impressions:** <impressions>, **Clicks:** <clicks>, **CTR:** <clicks/impressions
as a percentage>
**GSC window:** <startDate> to <endDate>

**Top-3 SERP snapshot:** <one line per result: rank, domain, title>

**What changed:** <title/meta rewrite, H2 + answer paragraph, N internal links>,
described plainly, e.g. "Rewrote the title and meta description to match the
query's commercial intent, added an H2 that directly answers '<query>' with a short
answer paragraph, and linked to <related page> and <related page>."

<!-- openseo-evidence
project: <projectId>
query: "<query>"
page: <page URL>
baselinePosition: <position>
baselineWindow: { start: <startDate>, end: <endDate> }
measureAfter: <a date 28+ days after expected merge>
-->
```

The fenced `openseo-evidence` YAML block is machine-readable and deliberately
boring: it exists so a future run of this skill (or a person) can re-query the same
query/page/window later and report an honest before/after delta. This skill does
not currently do that follow-up itself; see below.

Tell the user the PR is ready for human review. Do not merge it yourself.

## Output format

After each phase, give a short status, not a wall of text:

- Preflight: pass/fail per check, and which one stopped the run if any did.
- Diagnosis: the candidate table, then the chosen query/page.
- Context: a 2-3 sentence read of the SERP (intent, who's winning, why), and the
  located source file for confirmation.
- Fix: a short diff summary before opening the PR (what changed, in the whitelist's
  own terms).
- Result: the PR URL and a one-line summary of the evidence block's numbers.

## Guardrails

- Repo-backed sites only. No CMS write path, no client-side/edge workaround, no
  "this works everywhere" claim. Refuse cleanly and explain why when preflight
  fails.
- Never guess the source file silently; always show it and get confirmation first.
- Stay inside the fix whitelist even under pressure to do more. JSON-LD/FAQ schema
  and any JS-injected change are permanently out of scope for this skill, not just
  today's run.
- `get_serp_analysis` costs real credits. State that before calling it, and call it
  once per run for the chosen query only, never for the full candidate list.
- Never open a PR with a build you have not verified passes.
- Never claim a merged PR "caused" a ranking or traffic change. This skill only
  predicts and proposes; it does not measure outcomes in v1. If the user asks for a
  post-merge readout, tell them to re-run `get_striking_distance` for the same
  query/page after the window in `measureAfter` and compare manually, or wait for a
  future version of this skill that automates it.
- One query, one page, one PR. If the user wants several pages fixed, run the skill
  again per page rather than batching edits into one PR.
